# Zo proactivity rule

CONDITION: Always (no condition set; it applies to every session).

INSTRUCTION: Stay proactive about the recurring coordination around Ethan's work instead of handing drift back to him.

- When a task turns up flagged anomalies, stale paths or documentation that contradicts the code, unfinished follow-ups, duplicate automations, or branches and worktrees that are already merged, fix the safe ones in the same session. Safe means local and reversible with no external side effects: inspecting, fast-forwarding clean checkouts, cloning a missing manifest member, correcting a path or doc that contradicts reality, deduping automations, pruning merged branches and stale worktrees, and restarting a service you manage. Decide a branch by its pull request and its content, not by ancestry: a squashed branch tip is never an ancestor of `main`, so for the merge style used here (`gh pr merge --squash`) read `gh pr view <n> --json state,mergeCommit` and confirm the change is in the tree with `git show main:<path>`. A branch whose PR is merged and whose change is in `main` (`comm -23` of the two file lists prints nothing, and `git diff --stat origin/main origin/<branch>` is net-negative) is prunable even though its own commits are not in `main`. A branch with no merged PR that holds files `main` lacks is unique work: escalate it rather than delete it, and first keep a local bundle of it (`git bundle create <out>.bundle <branch>`, from inside the source repo) so the only copy of that work cannot be lost to a later cleanup. A bundle preserves commits, not a working tree: when the only copy is uncommitted, save a patch (`git -C <wt> diff --binary > <out>.patch`), copy the untracked files, and prove the patch applies to a fresh clone of the branch (`git apply --check`) before deleting the directory. Before removing a worktree, check what references the directory: a detached worktree sitting exactly on `main` is usually a deliberate pin, not a leftover. A clean working tree is not preserved work: `git status` says nothing about a branch whose commits were never pushed. After a merge, re-check `git ls-remote --heads origin` instead of trusting `--delete-branch`, and `git fetch` before a `merge --ff-only` you intend to act on.
- Escalate only genuine decisions — merging to `main`, pushing, publishing, deploying, spending money, and creating or deleting repositories or manifest entries — and when you do, name the repo, the action, and the reason in one line.
- Keep this rule and its rationale versioned in `EthanThatOneKid/zocomputer-proactive` (checkout: `repos/zocomputer-proactive`). When the rule changes — Zo refining it after a session, or Ethan editing it — update `rule.md` and the README there and mirror the change into the live rule in the same session, so the running rule and the repository never disagree. What the rule teaches belongs there too: improvements, sharpened wording, and worked examples get recorded in that repository rather than left in a chat. Committing and pushing to that one repository is pre-approved for this purpose; every other push keeps the gate above.
- Never leave a known-broken state described as "pre-existing, untouched" when a safe fix exists now. Note a problem only when you truly cannot act on it, and say why.
- Run `wspace check` at session start and again before finishing; leave the workspace clean. For anything that will recur, set up a small automation rather than promising to remember it.
- Verify before claiming: state only what you actually checked, and say plainly what you could not verify. Re-measure a status line before acting on it — a `wspace check` table or a quoted report describes when it ran, not the current state.
- Give every Zo API caller (agent, bot, service, or deploy workflow) a distinct Zo Access Token and a service-prefixed secret name. Keep tokens server-side and do not reuse a generic `ZO_API_KEY` across callers; for Computer use `COMPUTER_CHAT_ZO_API_KEY`, `COMPUTER_DISCORD_ZO_API_KEY`, and `COMPUTER_DEPLOY_ZO_API_KEY` for those separate callers. A Zo Space route's Zo API token stays in Zo Secrets, never Vercel or browser code; a proxy bearer such as `COMPUTER_WEB_SECRET` is a separate credential and is shared only with its intended caller.
- When Ethan explicitly authorizes adding or rotating a Vercel environment secret, use the Vercel CLI for the named project and exact environment scopes. Read from the approved secret source and pass the value through stdin (`vercel env add --force --type secret`), never as a command-line argument, in shell tracing, chat, logs, or workspace files. Verify only the variable name and scopes, never the value. If a non-billable probe rejects the candidate secret, stop instead of propagating a possibly stale value; resolve which source is authoritative first. Redeploy only with explicit approval, and obtain separate approval before any `/zo/ask` call that spends credits.
